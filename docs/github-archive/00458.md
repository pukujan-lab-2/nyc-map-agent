# PR #458: feat(assets): version history for published tiles and a build asset manifest

- State: closed (2026-10-25)

- Branch `feat/asset-history` into `main`, +448 −26 in 9 files

The tile sets the map reads (city buildings, tax blocks) are published to storage, and the database kept only the current version plus one previous version. Once a third version went up, there was no record of what a running build had been serving. This change keeps every version and has each build write down exactly what it ships.

**What changes**
- **History table:** a migration adds `core.published_asset_versions`, keyed by asset name and sha256 etag. Each row holds the version's parts, and records when it was published, when another version replaced it (`retired_at`) and when its stored files were deleted (`pruned_at`). It backfills from the current and previous columns already in `core.published_assets`.
- **The current pointer stays where it is:** `core.published_assets` is still what `/api/city-tiles` reads, so serving is unchanged. A new foreign key means it can only point at a version that's in the history. The down migration drops the key and the table.
- **Publishing writes history:** `scripts/publish-city-tiles.ts` records the new version before it moves the pointer. Then it stamps `retired_at` on the version it replaced, and stamps `pruned_at` once the old files are actually deleted. If the key can't delete files, nothing is stamped.
- **Build manifest:** `vite build` writes `asset-manifest.json` next to `index.html`. It lists each shipped file with its size and sha256, plus the commit. The image build has no `.git`, so the deploy pipeline passes the commit as `GIT_SHA`.

**How to answer "which tiles was this build serving?"** Read `commit` from the site's `/asset-manifest.json`, find that commit's deploy time, and take the row per name where `published_at <= deploy time < retired_at` (or `retired_at` is still empty).

**Evidence**
- A local `pnpm build:size` wrote a manifest listing 87 files with the right commit, at 16 kB. All size limits still pass.
- Nothing this change could break failed: 1237 unit tests pass, including the 2 new manifest tests and the existing deploy-pipeline tests. Typecheck, lint and module boundaries are clean.
- Docker isn't available on this machine, so the up/down/up round trip for the new migration runs only in the CI `migrations` job on this PR.

**What stays the same:** how tiles are served, the one-previous rollback columns, and the prune rules.

**Caveat:** the deploy service runs its own container, so the `GIT_SHA` change in `deploy/cd/pipeline.ts` takes effect only after that service is rebuilt. Until then, production manifests show `commit: null`, and the file hashes still identify the build.
