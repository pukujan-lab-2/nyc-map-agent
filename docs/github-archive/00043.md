Closes #30

- `pnpm publish:city-tiles` uploads `public/tiles/nyc-city.pmtiles` (82.1 MB) through Octo `/api/files/upload` + `/publish` (R2, public bucket at files.design-bakery.com) in 2 parts of ≤40 MiB — a single base64 upload is ~110 MB and the edge rejects it (502, 100 MB request cap). Parts + sha256 etag recorded in new `core.published_assets`.
- `GET /api/city-tiles` (Hono app, so any host): answers PMTiles Range requests same-origin, stitching ranges across parts; ETag/If-Match, `Accept-Ranges`, 416 for bad ranges, `Cache-Control: public, max-age=86400`, CORS `*` + exposed Content-Range/ETag for cross-origin frontends. Excluded from gzip. Manifest cached 10 min.
- Default `VITE_CITY_TILES_URL` is now `/api/city-tiles`; local file still works by setting it to `/tiles/nyc-city.pmtiles`.

Why a proxy: Octo's public R2 URLs do Range (206, ETag, Accept-Ranges) but send no `Access-Control-Allow-Origin` and 403 the OPTIONS preflight, so a browser on the app's origin can't read them directly.

Verified: curl with `Origin: http://localhost:5174` + Range at file start, across the part boundary and near the end → 206, correct Content-Range, bytes identical to the local file. Headless Chrome street level at Graham Ave & Cook St and Fulton/Smith (1440 + 390): 19 tile range responses from /api/city-tiles, textured buildings render (eye2-octo-*.png). Unit tests for range parsing / part slicing.
