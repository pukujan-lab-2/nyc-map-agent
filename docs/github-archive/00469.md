## Problem

On a phone, the site stays blank for seconds before anything appears. The page and its styles arrive in under half a second, but the app's 2 MB script starts running straight away and keeps the browser from drawing. A phone-speed Lighthouse run (Google's page-speed tool) on the live site saw the first paint at 2.3 s and scored 42.

## What changes

- **The chat bar paints first.** `src/main.tsx` is now a small loader. It waits one frame, so the static chat bar from `index.html` is drawn, and then loads the app (`src/boot.tsx`, the old `main.tsx`). A build-only Vite plugin adds `modulepreload` links, so the app's files download alongside the page rather than after it. A 200 ms timeout covers background tabs, where animation frames do not run.
- **The app's styles no longer block the first paint.** They load with the app instead of in the page head.
- **The static bar shows its mic and voice icons**, so it matches the real bar and counts as visible content.
- **The map library (maplibre-gl) gets its own file.** It is about half the download and rarely changes, so phones keep it cached when we deploy.
- **Hashed build files (`/assets/*`) are cached for a year** (`immutable`). Before, they were cached for 4 hours. Missing files still return 404.
- **Size budgets follow the new files:** loader 12 kB, app 275 kB, map library 255 kB, all JS 1065 kB (+5 kB of chunk overhead).

## How to verify

- In a slowed browser (4× CPU, slow 4G, 390×844, 4 runs each against local builds), the first paint arrives in **about 0.2 s instead of about 0.8 s**.
- After deploying, open https://nyc.design-bakery.com on a phone. The chat bar with its icons should appear at once, and the map should follow.
- Unit tests pass (1277), all 32 end-to-end tests pass, and lint, knip (the dead-code check) and the size budgets pass.

## What stays the same

Typing into the static bar before the app loads still carries over (`shellDraft`). The stale-build reload guard is set up in the loader before anything else loads.
