Each tab made about 28 live-data requests on first load (34 segment requests in production) and polled every 15 seconds, and idle visible tabs kept polling forever, so server load grew with every open tab.

## What changes
- **`/api/transit-live?systems=…&alerts=1`**: requested rail systems plus alerts in one response, reusing the existing 15 s server cache (no extra MTA calls). Weak ETag, 304 on a matching `If-None-Match`, `Cache-Control: public, s-maxage=30, stale-while-revalidate=30`. A failing system is listed under `failed`; 502 only if all fail.
- **`/api/transit-segments/all?routes=…&dow=&hour=`** replaces the per-line requests; edge-cacheable for 6 hours with the hour in the URL.
- Client: the map, status drawer and cards share one poll every 30 s. Old endpoints still work. Both new endpoints are in the OpenAPI spec.
- **Idle pause (part of #369)**: after 10 minutes without pointer, key or touch in a visible tab, transit polling stops (buses too) and a "Live updates paused — tap to resume" button appears. Mounted through the transit feature's overlay slot.

## How to verify
Local server: first load made one `transit-live` and one `segments/all` request instead of about 28; real data returned (431 trips, 125 alerts, 312 KB gzipped); a repeat with the ETag returned 304; with a temporary 5 s timeout (reverted) the pause appeared, no requests went out for 40 s, and a tap resumed. Typecheck, eslint, 99 tests, the module-boundary check and `openapi --check` pass.
