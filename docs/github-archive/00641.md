# Issue #641: The agent repeats the earlier tool, narrates itself and speaks internal names

- State: closed (2026-11-01)
- Opened by Pukujan on 2026-11-01
- Original: https://github.com/Pukujan-lab/nyc-map-agent/issues/641

### Summary

After testing nyc.design-bakery.com the owner called the agent "still too dumb". The last day of traces in the NYC Octo workspace (2026-11-01, about 15:52 to 15:57 UTC, all LFM3) show five faults. (1) After a restroom question, "get to times square" was answered with the nearest restroom again. (2) "Let me go to Brooklyn Bridge" got a reply that narrated its own reasoning ("Let me find the nearest public restroom first...") and called no tool. (3) The same reply invented a route ("take the E train up to the Brooklyn Bridge entrance") without calling transit_plan, then asked which mode the rider wanted. (4) Tool names, trip ids and raw data reached the rider ("tap the walkToNearest button for trip 234443bb-...", "Open later seasonally"). (5) Trip turns took 14.8, 18.1 and 19.3 seconds; transit_plan itself took 1.8 to 2.8 seconds. The traces also cannot show why: tool spans carry only the tool name.

Wanted: each turn is read from its own latest message, so a new destination never repeats the earlier tool; the model cannot answer a trip request without calling a tool; nothing internal reaches the rider; trip turns make fewer model calls; and tool spans carry arguments, a result summary and an outcome.

### Acceptance Criteria

1. After a restroom question, a message asking to go somewhere calls transit_plan, not nearest_restroom, and the reply says nothing about the earlier topic.
2. A new request cannot be answered without a tool call: the first model step must call a tool.
3. No tool name, trip id or raw schedule text such as "Open later seasonally" reaches the rider.
4. A planned trip takes two model calls, not three: transit_plan draws the route and opens the panel itself.
5. Tool spans carry the arguments, a short result summary, and an OK or ERROR status; the turn span says what kind of turn it was.
6. Automated tests cover 1 to 5. Deployed to nyc.design-bakery.com.

### Boundaries and Next Action

In scope: the chat route's per-turn tool rules, the reply filter, the restroom hours text, the trip tool drawing its own route, and span attributes. Out of scope: model choice (decision 0009 stands), confirmations (the owner rates this agent low stakes), and the ask-or-plan slots from #626. Next action: add the per-turn tool rules to the chat route.

### Symptoms

1. **Stale topic:** "get to times square" after a restroom question called nearest_restroom and answered about Moore Homestead Playground (19.3 s).
2. **Reasoning in the reply:** "Let me go to Brooklyn Bridge." was answered with "Let me find the nearest public restroom first..." and no tool call.
3. **Invented route:** the same reply named the E train without calling transit_plan, then asked "Want me to get you a walking route or transit plan?".
4. **Internal names:** a reply said "tap the walkToNearest button for trip 234443bb-..." and read "Open later seasonally" aloud.
5. **Slow turns:** trip turns took 14.8 s, 18.1 s and 19.3 s; transit_plan took 1.8 to 2.8 s of that.
6. **Thin spans:** tool spans carry only tool.name and every span has status UNSET.

### Hypotheses (unverified)

H1. The earlier restroom answer in the history steers LFM3 to repeat nearest_restroom, and the model is free to answer in text with no tool. **Status:** unverified. **Would confirm:** with nearest_restroom unavailable and a tool call required on the first step, "get to times square" plans a trip. **Would refute:** it still talks about restrooms. **Experiment:** replay the two-message conversation against LFM3 after the change.

H2. The extra seconds are model round trips: the model calls transit_plan, then showRoute and openPanel in later steps, then writes the answer. **Status:** unverified. **Would confirm:** step timings in the run log show three model calls per trip. **Would refute:** two calls but slow generation. **Experiment:** time a trip turn before and after transit_plan draws its own route.

### Counter-signal

One 0.4 s turn happened when no model work was needed, so the fast path and tools are quick; the time is in the model calls.

### Honest Caveat

The five faults come from a handful of spans on one afternoon. How often the model repeats an earlier tool is not measured.

### Problems vs Gaps

Problem: wrong tool, invented routes and leaked internals reach riders. Gap: the route has no per-turn rule for which tools may run, no filter on the reply, and spans too thin to diagnose from.
