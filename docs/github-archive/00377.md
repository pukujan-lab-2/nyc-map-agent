After #343 deployed, the live agent answered plain questions 3 times out of 3, but a trip question ("Times Square to Brooklyn Bridge by subway") still ended in "The model call failed." The transit_plan tool ran, then the model's follow-up call failed with InferHub's "every provider within your price limit is busy or rate-limited" message. The server log showed that message and none of the "busy; retrying" lines #343 added, so the retry never saw it.

## What changes
- InferHub can answer HTTP 200 and put the error in the first chunk of the stream, so the status looks fine. `fallbackFetch` now reads the first chunk of a copy of a 200 response (waiting at most 3 s), and treats an error message there like a failed call: retry the same model twice, then fall to the next model. The caller's own copy of the stream is untouched, and a normal stream adds no delay.
- The in-stream cause is inferred from the missing retry log lines, not seen directly: the busy answer is intermittent and I could not capture the raw bytes. If trip questions still fail after this deploys, the log will say why.

## How to verify
- Unit tests (15 in the file): the error is read from the first chunk, a normal stream is left whole, a busy 200 stream is retried then succeeds, and a stream that stays busy falls to the next model. Typecheck and lint pass.
- After deploy, ask the live agent a trip question a few times; it should answer instead of failing.

## Unchanged
- Plain HTTP-error handling from #343, the key, the models, and what the client sees on a final failure.
