### Summary

The chat's answers about subway lines can be wrong even when its tools return the right data (#627), and nothing measures how often. This asks for a repeatable way to find those errors on many cases, change one thing, and see whether the pass rate moved, run for long stretches on the owner's own machines and driven by a cheaper outside model (DeepSeek).

### Identity and Lineage

Repository Pukujan-lab/nyc-map-agent. Builds on #627 and PR #628 (the first fix) and on `scripts/eval-trip-questions.ts` (#625, the existing live check). Related: #594 (estimates never scored against outcomes), #601 (Phoenix traces).

### Acceptance Criteria

1. `pnpm`-free command `tsx eval/line-status/run.ts` runs saved cases against the app's agent with the alert feed replaced by a recorded snapshot, several trials each, and prints a pass rate per check and per split (train, held-out).
2. Rule checks and metamorphic rules are unit-tested offline, including the real wrong A-train reply from #627.
3. A recorder saves the live MTA alert feed as timestamped snapshots, so past moments can be replayed.
4. Every run row records the model, prompt hash, tool-shape hash and git commit.
5. A written iteration protocol and handoff in the repo lets DeepSeek run the loop alone, with its limits.
6. Real rider questions are not collected until docs/PRIVACY.md and docs/DESIGN_RULES.md describe it (see the decision below).

### Symptoms

1. **One case fixed by hand:** #628 fixed the A-train answer we happened to notice; no test asks the model.
2. **No pass rate:** nothing says how often line status answers are right, so a prompt change cannot be shown to help or hurt.
3. **No past moments:** the alert feed is not archived, so a day with unusual service changes cannot be replayed.

### Hypotheses (unverified)

H1. Rule checks over many trials expose more reading errors than the one found by hand. **Status:** unverified. **Would confirm:** the first run on the current prompt shows a pass rate below 100% on checks other than the one from #627. **Would refute:** it passes everything on several trials per case. **Experiment:** run the harness on LFM3 with the cases in the repo.

H2. A typed or shorter tool result improves the pass rate more than prompt rules do. **Status:** unverified. **Would confirm:** a result-shape change moves the pass rate on held-out cases more than a prompt change. **Would refute:** the reverse. **Experiment:** compare two runs that differ in one of them.

### Counter-signal

The tool result for the A train was correct against the live MTA feed on 2026-11-01. The harness therefore measures the model's reading and not the data, and says nothing about whether the MTA's own alerts are right.

### Honest Caveat

LLM output varies run to run, so a single pass proves little; the harness reports rates over repeated trials. A model that is tuned to the cases it sees gets better on them and no better in general, which is why a held-out split exists.

### Problems vs Gaps

Problem: errors in line status answers go unmeasured. Gap: no archive of alert feeds, no cases, no scoring, no loop.
