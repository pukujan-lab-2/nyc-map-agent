# PR #193: Keep one previous published asset version and prune older Octo files

- State: merged (2026-10-22)
- Opened by Pukujan on 2026-10-21
- Original: https://github.com/Pukujan-lab/nyc-map-agent/pull/193
- Branch `fix/prune-published-assets` into `main`, +176 −5 in 4 files, merge commit 080715496f7be20b48b90579ac47eea087413506

Each rebuild of a large static asset uploaded a new multi-part copy to Octo files and never deleted the old one, so storage grew by a full copy per publish (about 680 MB orphaned today).

## What changes
- Migration `20261021200000_published_assets_previous.sql` adds `previous_parts`, `previous_etag`, `previous_total_bytes` to `core.published_assets`.
- `scripts/publish-city-tiles.ts`: upload, then verify (every part fetchable, per-part and total bytes, sha256 etag), then swap (old current moves to previous), then delete the Octo files of the version that was previous before the swap.
- Ids of the current and previous versions are never deleted. If verification fails the script exits non-zero, deletes nothing and keeps the old pointer.
- A 403 from `DELETE /api/files/:id` logs `prune skipped: key lacks delete scope` and the publish still succeeds. Pruning needs an `OCTO_API_KEY` with the `delete` scope and an owner/admin workspace role (documented in the script header).
- `--dry-run` prints what would be uploaded and pruned without changing anything.
- `scripts/asset-prune.ts` holds the pure selection and verification logic; `scripts/asset-prune.test.ts` covers it.

## How to verify
`pnpm test scripts/asset-prune.test.ts`; `pnpm publish:city-tiles -- --dry-run`.

## Unchanged
`/api/city-tiles` still reads `parts`; existing rows work as before (previous is null until the next publish).
