# Issue #627: The chat told a rider to change trains at stops the A skips

### Summary

Asked "Is the A train running near Times Square right now?", the live chat gave a wrong, confusing answer even though its line status tool returned correct data. It put delays at Times Square "in both directions", told the rider to change trains at stops it had just said the A skips (High St, Fulton St, Chambers St, Canal St), and ended "Want to start?" with nothing to start.

### Identity and Lineage

Repository Pukujan-lab/nyc-map-agent. Code: the `line_status` tool in `server/features/agent/tools.ts` and the rules in `server/features/agent/prompt.ts`. Related: #361 (line status on recorded MTA data), #375 (the agent never guesses).

### Acceptance Criteria

1. The tool's result names the lines that still stop at a skipped station in a key that cannot be read as a place to change trains.
2. The prompt tells the model to say a delay's direction and place exactly as the tool gives them, to never send someone to change trains at a stop the tool says is skipped, to say whether the trouble touches a station the rider named, and not to close a status answer with "Want to start?" when no trip was planned.
3. `prompt.test.ts` and `trouble.test.ts` pass with those changes.
4. The same question on nyc.design-bakery.com no longer names a skipped stop as a place to switch.

### Boundaries and Next Action

In scope: the tool's result shape and the prompt text. Out of scope: switching the chat model, and what the MTA feed says. Next action: rename the key, add the prompt rules, add tests, open a pull request.

### Symptoms

1. **Invented place and direction:** the feed says "Downtown A trains are running with delays while we conduct track maintenance on the line throughout Manhattan"; the chat said delays "in both directions at Times Square".
2. **Skipped stops offered as switch points:** the chat said to "switch at High St or Fulton St/Chambers St/Canal St". The tool result lists those as stops Inwood-bound A trains skip, with the other lines that stop there under `otherLinesAtSkippedStations`. Its only real switch points are Nostrand Av and Utica Av, for Queens-bound trains.
3. **Unasked closing question:** the answer ended "Want to start?" although no trip had been planned.
4. **Question not answered:** none of the A's troubles touches Times Sq-42 St, but the answer never said so.

### Hypotheses (unverified)

H1. The model read the keys of `otherLinesAtSkippedStations` (High St, Fulton St, Chambers St, Canal St) as where to switch. **Status:** unverified. **Would confirm:** after the key is renamed and the prompt rule added, the same question stops producing that advice. **Would refute:** it still names skipped stops. **Experiment:** ask the live chat the same question five times after the fix.

H2. The broad rule "end an answer about a place with Want to start?" bleeds into status answers. **Status:** unverified. **Would confirm:** status answers stop ending that way once the status rule says so. **Would refute:** they keep doing it. **Experiment:** same as H1.

### Counter-signal

The tool result itself is correct (run against the live MTA feed on 2026-11-01): the delay text, the skipped stops and the Nostrand Av and Utica Av switch points all match the MTA's alerts. So the fault is in how the model reads and restates it, not in the data.

### Honest Caveat

One question was tried, twice, on one model (LFM3 on the owner's MacBook Pro). A prompt rule lowers the chance of a wrong answer but cannot guarantee one, so the check after deploy is a handful of asks, not one.

### Problems vs Gaps

Problem: a rider can be told to change trains at a stop the train skips. Gap: nothing tests how the model restates a line status result; the tests only check the tool.
