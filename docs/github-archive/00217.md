# PR #217: feat(db): asset version history by name+sha256 and a build asset manifest

`core.published_assets` kept one row per asset name (plus, with #193, one `previous_*` slot), so there was no record of which tile set a given app build was made with, and nothing older than one version back to roll back to.

> **Stacked on #193** (not merged yet). Merge #193 first; this PR's base then moves to `main`.

**What changes**
- Migration `20261021210000_asset_versions.sql`:
  - `core.asset_versions`: one row per upload, primary key `(name, sha256)`, with `parts`, `etag`, `published_at`, `pruned_at`.
  - `core.asset_current`: `name → sha256` pointer (foreign key into the history).
  - Backfills current and #193's previous version from the old table, then replaces `core.published_assets` with a **view of the same columns**, so `api/city-tiles.ts` and `scripts/build-aggregates.ts` are untouched.
  - Down rebuilds the #193-shaped table from the view, then drops the new tables.
- `scripts/publish-city-tiles.ts`: records the version and moves the pointer in one statement. Keeps #193's verify-before-swap and its rule of one rollback version with files. Deletes the Octo files of older versions but keeps their history rows (`pruned_at`). If a file's sha256 already exists as a stored version, it only moves the pointer. `--dry-run` reports all of this.
- `scripts/asset-manifest.ts` runs after `vite build` (`pnpm build` and the `Dockerfile`) and writes `dist/asset-manifest.json`: app name/version/commit, sha256 and size of every bundled tile/model, and the `core.asset_current` pins when `OCTO_*` is set (otherwise `published: null`).

**Verify:** Postgres 16.4, local: data round-trips: seeded #193 rows → up (the view shows the same current/previous) → down (table restored) → up. Ran the publish SQL by hand: three publishes leave s3 current, s2 rollback, s1 pruned. `pnpm test` 169 pass, including new `versionsToPrune`, `assetSha256` and manifest tests.

**Not done (follow-up):** `/api/city-tiles` always serves the current pointer. Serving a build's pinned sha256 would change the client, and UI work is paused.

**Needs before running in prod:** `pnpm db:migrate` after #193's migration. Run the publish script only after this migration.
