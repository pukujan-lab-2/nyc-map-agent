Every speed change so far has been judged against warm loads on a fast Mac, so nobody knew how long a cold load takes on a phone. This adds that number and a script that reproduces it.

Closes #362

## What it found

On a phone-speed CPU and a slow 4G link, the map appears after about 5 seconds and the page is ready to use after about 9. Most of the wait is the main script running, not the download: the main bundle alone spends 3.6 s on a CPU four times slower than the Mac's.

| Score (out of 100) | First paint | Largest paint | Blocking time | Ready to use | Requests | Transferred | Main bundle script time |
|---|---|---|---|---|---|---|---|
| 42 | 5.1 s | 8.9 s | 0.9 s | 8.9 s | 55 | 1.30 MB | 3.6 s |

These are medians of three runs of Lighthouse 13.5.0's mobile preset against the live site (main `613d0ca`).

## What changes

- **`scripts/perf-throttled.ts` (new).** It runs Lighthouse's mobile preset a few times and prints the medians as a Markdown table. It uses Playwright's own Chromium unless `CHROME_PATH` is set. Run it with `npx tsx scripts/perf-throttled.ts [url] [runs]`.
- **`docs/PERFORMANCE.md`** gains a dated "Emulated mid-range phone" section with the table, the device, the build, what isn't counted, and why a first attempt was thrown away.

## Worth knowing

- Lighthouse rather than plain Playwright. A Playwright and developer-protocol version reported 31 requests and 0.65 MB, because neither sees the map's tile worker. It also read the main thread as 99.9% busy even without a slowdown, because the map's software drawing never stops in a headless browser.
- Tile bytes still read as 0 in Lighthouse, so 1.30 MB is a floor.
- Runs vary. An earlier single run measured 4.2 s of blocking time against this median of 0.9 s.

## What stays the same

No app code changes. The 2026-10-23 baseline and its idle-minute table stay as they were. The owner's own phone and work computer can be added later with the same script.
