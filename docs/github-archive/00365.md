# Issue #365: Live trains re-render the transit layer about 15 times a second

- State: closed (2026-10-25)
- Opened by Pukujan on 2026-10-24
- Original: https://github.com/Pukujan-lab/nyc-map-agent/issues/365

The live-train animation goes through React state, so the whole transit layer re-renders many times a second, and the console fills with React loop warnings. This likely costs CPU on every device.

## Symptoms
1. **Per-frame re-render**: `src/features/transit/TransitLayer.tsx` runs a `requestAnimationFrame` loop that, at most every 66 ms, calls `setVehicles([...next.values()])` (line 457 on `main`), re-rendering the component about 15 times a second.
2. **Loop warnings**: a local dev load on 2026-10-23 logged 158 "Maximum update depth exceeded" warnings from `TransitLayer`, plus "flushSync was called from inside a lifecycle method" from `addIcon`, which renders a React root inside a MapLibre event.

## Hypotheses
**Per-frame state updates cost noticeable CPU.** Status: unverified. Would confirm: a profile shows `TransitLayer` committing about 15 times a second. Would refute: commits are cheap in the profile. Experiment: React profiler during one minute of idle live trains.
**An effect loop causes the depth warnings.** Status: unverified. Would confirm: one effect re-sets state on every render. Experiment: find the effect that fires in the warning's stack.

## Caveat
The warnings were seen on a dev build with some API routes failing locally; they have not been checked on the production build.

## Acceptance criteria
- [ ] No "Maximum update depth exceeded" or `flushSync` warnings on load.
- [ ] Vehicle animation updates the map source directly, not React state; `TransitLayer` commits only when data changes.
- [ ] Idle CPU measured against the baseline.
