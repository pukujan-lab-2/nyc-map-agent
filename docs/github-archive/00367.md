# Issue #367: Cut network calls: one batched live endpoint cached at the edge

- State: closed (2026-10-25)
- Opened by Pukujan on 2026-10-24
- Original: https://github.com/Pukujan-lab/nyc-map-agent/issues/367

Every open tab polls our server often and with many separate requests, so server load and bandwidth grow with every tab, and a refresh repeats it all.

## Evidence (from the code on `main`)
- `src/features/transit/hooks.ts`: live trains and buses poll every 15 s (`REFRESH = 15_000`); alerts every 60 s.
- One `/api/transit-segments` request per subway line (34 on first load, seen in the browser's network list on 2026-10-23), each refreshed every 10 minutes.
- `server/features/transit/routes.ts` caches each MTA feed in memory for about 15 s, so upstream MTA calls do not grow with users; our server and bandwidth do.
- Response sizes were not measured.

## What is needed
- One batched live transit endpoint, polled every 30 to 60 s, with an `ETag` so unchanged data returns 304.
- `Cache-Control: public, s-maxage=30, stale-while-revalidate` plus a Cloudflare cache rule, so the edge serves most users and refreshes.
- The server syncs MTA feeds about once a minute.
- The 34 segment requests become one prebuilt static file cached for hours.

## Acceptance criteria
- [ ] First load makes one live-transit request, not dozens.
- [ ] A second visitor within 30 s is served by the edge (cache HIT header).
- [ ] Request count and bytes measured against the baseline.

The app side is in place: `/api/transit` and `/api/transit/alerts` send `public, s-maxage=60, stale-while-revalidate`, and live trains come from one batched request. **Pukujan commented, 2026-10-25**

Live transit answers are now served from Cloudflare's edge cache instead of hitting the server on every request.

Added a Cloudflare Cache Rule named `nyc-map live transit` for requests where the host is `nyc.design-bakery.com` and the path starts with `/api/transit`. These responses can now be cached. Cloudflare follows our own `cache-control` header (60 seconds at the edge, 30 in the browser) and skips caching when that header is missing.

Checked on the live site with three requests to `/api/transit/alerts`: the first was `cf-cache-status: MISS`, then `HIT` (age 2) and `HIT` (age 4).

None of the API tokens in the vault has the "Cache Rules" permission, so the rule was made in the dashboard.
