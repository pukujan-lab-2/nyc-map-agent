## In flight

**Subway trains on the map sat too long at stations and then crossed to the next one faster than a subway can go: 12.9% of the legs drawn in one live snapshot were faster than the fastest run a car can make (#257, branch `fix/257-train-run-first`, task NMA-0065; owner, 2026-11-20: "stop way too long in the station ... and then travel very fast between stops").** Where the feed gives no departure time, the map gave each station a fixed stop of 30, 50 or 60 s and took it out of the gap to the next arrival, so the run got whatever was left. The split now goes the other way: the run gets the time a train normally needs for its distance (1.5 times the fastest possible run, calibrated on seven days of subwaydata.nyc), and the stop gets the rest, up to the old default and never under 10 s while the gap allows it. On the same snapshot the racing legs fall to 0.5%; the median stop stays 30 s. Arrival times, departures the feed supplies and commuter rail are unchanged. Not done: real stop times per station (the feed gives two estimates for the numbered lines, 17 to 27 s and about 54 s, and none for the lettered lines), the trouble mode for delays and alerts, and a parked and racing score on the tracker health page.

**The Walk Guide counted in its own steps, so a rider who steps shorter was told "you should see the sign" too early: on our Union Sq recording the rider took 296 steps where the guide counts 212 (rider-walks loop, #186, branch `feat/186-rider-step-pace`).** The guide now learns a rider's pace when they confirm the next sign and counts their steps at that pace (`src/features/walkguide/progress.ts`, tests in `pace.test.ts`). Replaying that rider's counts, the prompt comes 95 steps too early in total without it and 50 with it; the split of steps between the mezzanine signs is an estimate, the totals are measured. Checked in the built app by hand: the steps to go change from 190 to the rider's own count after one confirmed leg. Not run here: the browser test at the four sizes, because this Mac has no Playwright browser; CI runs it. Also found: the MTA's 2021 draft station data still matches today's elevator list (all 308 of its elevators are in the live feed; the live feed has 122 more). Not built: a reset from an elevator ride, because a web page cannot read the barometer; that waits for the native app.

**One browser test failed about three runs in seven on 2026-11-20 and blocked pull requests that had nothing to do with it (branch `test/offline-replay-settle`).** `e2e/offline-replay.spec.ts`, the Spanish trip card with the network off, paused a fixed second after the card's second translation request before going offline; on the busy CI machine a later request was still on its way, so a line read in English ("Walk to Grand Central-42 St"). The test now waits until two seconds pass with no new request. Not run locally: this Mac has no Playwright browser, so CI's `e2e` job is its first run. If it still fails, the cause is in the card and not the pause.

**A NaviLens code could reset the Walk Guide's dot without a tap, but only NaviLens's own app reads those codes and they publish no reader (rider-walks loop, #186, pull request #261, branch `feat/186-navilens-reader`).** `src/lib/navilens/` is a reader of our own. It does not decode a code's meaning: it reads the 25 coloured cells as a pattern and looks that up in our own table. The owner said on 2026-11-20 that NaviLens gave permission and asked for it to sit in a folder that can be deleted if that is withdrawn; the folder's README gives the steps and a test keeps it isolated. In tests it reads made-up codes straight on, small, tilted to 25 degrees, squashed to 60% width and in dim, speckled pictures, and by hand it read the code image on navilens.com from a screenshot. It has not seen a real code in a station, its table is empty and no screen uses it. Next: photograph the codes on a filmed walk, fill the table, then let the Walk Guide's camera scan try the reader before it asks the server to read a sign.

**The app knew which elevators reach the street but not what a rider passes between the street and a platform (rider-walks loop, #186, pull request #263, branch `feat/186-station-pathways`).** `public/transit/pathways.json` now holds the MTA's draft station data for 230 station entries: 3,810 stairs, elevators, escalators, walkways and gates, most with the sign a rider follows. `src/lib/transit/pathways.ts` finds a route with no stairs or escalators and can leave out an elevator that is out of service; asked for the two routes we filmed on 2026-11-13 it returns the same elevators and signs, and it finds a step-free way to the street for 240 of the draft's 371 platforms. The owner has the MTA's permission to use the draft (2026-11-20); it is not on a feed, so `pnpm build:pathways <folder>` needs the unzipped draft. Nothing in the app reads the file yet. It has no positions inside stations, no levels and no distances: recordings add those. Next: let the chat agent answer "how do I get from the street to the platform without stairs" from it, with live outages.

**The chat could say which elevators were out at a station but not the way through it (rider-walks loop, #186, pull request #268, branch `feat/186-station-route-tool`, built on `feat/186-station-pathways`).** A new chat tool, `station_route`, gives the way between the street and a platform with no stairs, one step at a time: each elevator by its number and the sign to follow, from the MTA's draft station data, leaving out elevators that are out right now. With the only elevator out it says there is no way and when the elevator is due back; for a station the data does not hold it says the inside is not mapped. Tested against the Union Sq route we filmed and across every stop in the data (`server/features/agent/stationRoute.test.ts`). Not tried with a live model: the answers a rider reads have not been looked at yet. Next: ask it ten real questions on the test site and read the answers.

**Every drift number for the station guide came from one walk, and that walk turns out to be the odd one (rider-walks loop, #186, pull request #269, branch `test/186-more-recorded-walks`).** Two more recordings from 2026-11-13 were already in the project's Octo files (`station-walk-starter-pack/sensor-recordings/`): the evening walk through 14 St-Union Sq the other way, and the first leg at Cortlandt St. Their step and barometer rows are now test data (`src/features/recorder/replay/more-walks.json`, 27 kB) with a test. The Union Sq mezzanine took 296 steps in the afternoon and 218 that evening on the same phone, against 212 in the guide; Cortlandt St took 280 against 235. So the guide's counts are sound and a rider's pace belongs to one walk, which is why it is learned as they go. Also found: the ride finder reports the sloping Dey St passage (1.6 m down over about 40 seconds) as a ride with no length, so the ride count no longer matches the levels there. Next: make the ride finder tell a slope from a ride.
